# 便携式 Agent 操作系统：技术路线与功能清单

> 目标：一个 ≤ 8 GB 的便携镜像，内存上限 6 GB，内置 Agent 框架，可调用多家大模型 API，
> 作为主机的子系统运行（NAT / 桥接网络），换环境自动适配硬件，即插即用。
> 本文是技术路线草案，不是最终设计；标 ⚠ 的是需要你先做决定的地方。
>
> **已定决策（2026-10-01）：不内置本地模型，纯云端。** 它让镜像与内存都变得富余
> （见 §1、§2），但把网络从"能力之一"变成**硬依赖**，并且**没有任何本地回退**
> （见 §6 风险 1–3）。选型里的 `llama.cpp` 一项随之取消。

---

## 0. 先说结论

**可行，但先要做一个选择：它到底是哪种"操作系统"。** 你的描述里同时包含三种形态：

| 形态 | 启动方式 | 网络 | 主要成本 | 与你的描述吻合度 |
| --- | --- | --- | --- | --- |
| **A. 自启动 USB** | 目标机直接引导 | DHCP / 桥接 | Secure Boot、驱动、固件体积 | "即插即用"最贴切 |
| **B. 虚拟机镜像** | 宿主里当客机跑 | **NAT / 桥接** | 最低 | **"作为主机的子系统 + NAT/mirror"最吻合** |
| **C. 容器 / 便携运行时** | 宿主内进程 | 宿主网络 | 最低 | 但不满足"是操作系统" |

**建议 v1 选 B。** 理由有三：
1. 你原话的"作为主机的子系统"和"NAT 或 mirror"正是虚拟机网络模式（NAT / 桥接镜像）；
2. 两种网络模式在 VM 里都是配置项，不需要写驱动；
3. 调试成本最低，迭代最快。

**三者可以共用同一份 rootfs**，所以不是三选一：先把 B 跑通，A 与 C 后续由同一次构建产出。

**一个边界要先讲清**：虚拟机的 NAT 与桥接都是**宿主侧**设置，客机无权也无法感知——
它看到的永远只是一张以太网卡。所以"支持 NAT 或桥接"的正确含义是**同一镜像在两种模式下都能工作**，
而不是"镜像能自己切模式"；切换只能由宿主的部署脚本或文档指引完成（详见 §8 末节）。

**必须避免的一件事：不要自己写内核。** 这个目标的难点不在调度器或文件系统，而在
**固件、驱动、Secure Boot 与生态兼容**——那是几十年积累的护城河。正确做法是
基于 Linux 做**不可变镜像**，把创新集中在"硬件自适应 + 模型网关 + Agent 运行时"这三层。

## 1. 尺寸预算（目标 ≤ 8 GB）

| 组件 | 体量 | 备注 |
| --- | --- | --- |
| Debian minbase rootfs | 300–400 MB | `debootstrap --variant=minbase`，不含文档/man |
| Linux 内核 + initramfs | 100–200 MB | 单内核，模块按需 |
| 固件（裁剪子集：有线网卡 / 常见存储 / 常见 GPU） | 400 MB – 1.2 GB | ⚠ 全量 `linux-firmware` ≈ 1.5 GB，必须裁剪 |
| systemd + 基础工具 | 150–250 MB | |
| Python 3.12 + venv（Agent 与网关依赖） | 500 MB – 1.0 GB | **不含 torch/CUDA，也不含本地推理** |
| 可写层（配置 / 日志 / 会话 / 缓冲） | 1–2 GB | 纯云端下"会话记录"是主要增长项 |

**合计：2.5–5.3 GB**（区间取决于固件裁剪程度与可写层大小）。也就是说**不内置本地模型后，
8 GB 上限留下了 2.7–5.5 GB 的余量**——这笔余量怎么花，见下面第 3 条纪律。

**三条硬性纪律**：
1. **不装 PyTorch / CUDA**。仅此一项就是 3–5 GB；取消本地模型后它更不该出现——
   Agent 与网关都不需要 GPU 栈，装了纯粹是浪费。
2. rootfs 用 **squashfs 或 erofs** 只读压缩，实际落盘再省 40–50%。
3. **余量要记在账上，不默认花掉**。那 3–5 GB 是"可选项预算"：换成更大的可写层、
   更完整的固件子集（§6 风险 5），或日后重新评估本地模型都可以，但每一笔都要写回本文档，
   否则会以"顺手装个包"的方式悄悄消失——这是 8 GB 这类上限最常见的失守方式。

## 2. 内存预算（上限 6 GB）

| 运行模式 | 常驻内存 | 结论 |
| --- | --- | --- |
| 纯云端（**本决策**） | 约 1.0–1.5 GB | 6 GB 上限几乎用不到，2 GB 就已够用 |
| ~~云端 + 本地 4B Q4（8k 上下文）~~ | ~~4.5–5.0 GB~~ | 已排除（不内置本地模型） |
| ~~云端 + 本地 7B Q4~~ | ~~6.5–7.5 GB~~ | 已排除 |

**设计原则：护栏要挂在正确的地方。** 取消本地模型后，**6 GB 的主要威胁不再是模型，
而是 Agent 自己的上下文与文件缓冲**——一次读入一个 2 GB 文件、或把整个目录内容灌进上下文，
就足以打爆。所以：
- systemd 层仍用 `MemoryMax=6G` + `MemoryHigh=5G` 兜底，超限时**优雅拒绝新请求**而不是 OOM 杀进程；
- 但**主力护栏应在工具层与上下文层**：单次读取的大小上限、上下文窗口上限、并发上限——
  这三处才是纯云端架构下会先撞到的墙（对应清单 A5、D1）；
- 启用 zram（压缩内存）换取等效容量，但要如实标注"等效 ≠ 真实"；
- 启动时读实际物理内存：宿主只给 1 GB 时也能启动，但要把并发降到 1 并明确提示能力受限。

## 3. 技术选型

| 层 | 候选 | 建议 | 权衡 |
| --- | --- | --- | --- |
| 发行版 | Debian minimal / Alpine / NixOS | **Debian minimal** | Alpine 更小，但 glibc 缺失会让 Python 轮子与厂商固件工具链踩坑；NixOS 可复现性最好但学习曲线陡 |
| 镜像构建 | live-build / **mkosi** / debos | **mkosi** | 同一份配置可产出 ISO / 磁盘镜像 / qcow2 / 容器；live-build 只擅长 Debian ISO |
| 只读 rootfs | squashfs / erofs + overlayfs | **erofs + overlayfs**（可选 dm-verity 验签） | overlay 让"只读系统 + 可写状态"边界清晰 |
| 引导 | systemd-boot / GRUB | systemd-boot + **shim/MOK** | Secure Boot 绕不开签名 |
| 模型接入 | 各家 SDK 直连 / **LiteLLM** / OpenRouter | **LiteLLM 代理** | 一次配置 100+ 家 provider；Agent 只认一套 OpenAI 协议 |
| ~~本地推理~~ | ~~llama.cpp / Ollama / vLLM~~ | **已取消** | **不内置本地模型**（2026-10-01 决策）；日后若恢复，再单独评估 |
| Agent 框架 | OpenAI Agents SDK / Pydantic AI / smolagents / LangGraph | **用现成的**（默认 OpenAI Agents SDK，可换） | **不自研**（2026-10-01，ADR-6）：工具循环、上下文管理、重试预算是最容易写错也最不值钱的部分；自研的只剩"策略半层" |
| 硬件画像 | lspci/lsusb/dmidecode/udev | **自研 hwprofil`d`**，输出 JSON | |
| 持久化 | 加密分区 / LUKS 文件 / 无痕 | **按 machine-id 的加密持久层 + 可选无痕模式** | |
| 密钥管理 | 内置（禁止）/ 首次输入 / TPM | **首次输入 + 加密存储，永不入镜像** | 便携介质易丢，必须加密 |

**架构上最关键的一条**：**一切模型都走一个 OpenAI 兼容端点**，由本机 LiteLLM 代理聚合
多家云端 provider，Agent 侧只写一套客户端代码。这一条决定了"支持多种大模型 API"
是配置问题而不是代码问题。

取消本地模型后，这个端点**只剩下云端一侧**，于是"端点不可用"直接等于"Agent 不可用"。
因此**多 provider 主备、断线降级提示、流式中断恢复**这三项从"可选优化"升级为基线——
它们此前有本地模型作为退路，现在没有了。

## 4. 功能清单

### MVP（先把闭环跑通）
- [ ] 可启动镜像（UEFI + BIOS），进到命令行
- [ ] 硬件画像：CPU、内存、磁盘、网卡、GPU → `profile.json`（开机生成并留存）
- [ ] 网络自适应：DHCP 自动；失败回退 link-local；VM 下 NAT / 桥接可选
- [ ] 模型网关：LiteLLM + 至少 3 家云端 provider 可在命令行里配置与切换；**其中至少 2 家配成主备**（无本地回退）
- [ ] Agent 运行时：多轮对话、文件读写工具、shell 工具（**默认需人工确认**）、会话记录
- [ ] 密钥：首次运行向导 → 加密保存；**镜像内不含任何凭据**
- [ ] 内存护栏：`MemoryMax=6G`，超限返回明确错误
- [ ] 持久化：配置与会话跨重启保留；按 machine-id 区分不同机器

### V1（可用、可信）
- [ ] 工具沙箱：bubblewrap + seccomp，出网白名单
- [ ] **无网络时的明确降级**：只提供文件与 shell 工具，命令行如实说明"当前无法对话"，
      并保留待发消息到网络恢复——**不允许"看起来能用但一直转圈"的状态**
- [ ] **出网数据边界**：可配置敏感路径排除；工具读取被排除的文件时，发送前明确提示
- [ ] 换机感知：启动时对比 profile，提示"环境已变化：新网卡 / 新 GPU / 内存变化"
- [ ] 镜像签名 + SBOM + 校验和；自动更新走 A/B 分区或 overlay 原子切换，失败自动回滚
- [ ] 三种交付形态一键产出（USB / VM 镜像 / 容器）

### V2（扩展）
- [ ] GPU 加速按需下载（CUDA / ROCm）——仅当日后恢复本地推理才有意义
- [ ] 多机状态同步（端到端加密，可选）
- [ ] 多 Agent 编排、定时任务
- [ ] 只读介质运行（光盘 / 网络启动）

## 6. 硬约束与风险（这些是真正会挡住你的东西）

> 取消本地模型让体积与内存的账变轻松了，但把三条**结构性**风险顶到了最前面。
> 下面 1–3 是本决策直接带来的，4–9 是原本就存在的。

1. **网络即命脉** ⚠（本决策带来）—— 没有网络就没有对话。这不是体验问题而是**可用性问题**：
   断网时产品退化成一个普通文件编辑器。缓解：启动即探测连通性、多 provider 主备、
   断线时给出明确文字说明而不是转圈。**这条要写进产品说明的醒目位置，不能只留在文档里。**
2. **数据全部出境** ⚠（本决策带来）—— 本地模型是唯一"数据不出本机"的方案；不内置它，
   意味着**对话内容与工具读到的文件内容都会发送到 provider**。对个人日常使用可以接受，
   对"用 Agent 处理敏感文件"则不可接受。缓解：敏感路径排除、出网白名单、
   明确提示哪些内容正在离开本机。**这一条是否可接受取决于你的真实使用场景**——
   若答案是否定的，本地模型就不是可选项而是必需品，需要回到 §1 重算预算。
3. **密钥成为单点**（本决策带来）—— 没有本地回退，所以密钥失效 / 欠费 / 被限流
   都会立刻中断服务。至少配置两家可切换的 provider，并让用量与错误在命令行上可见。
4. **Secure Boot** ⚠ —— 开启安全启动的机器无法引导未签名镜像。必须用 `shim` + MOK 注册，
   或要求用户手动关闭。**这是"即插即用"的第一道坎，也是 A 形态最大的成本。**
5. **固件体积** ⚠ —— 现代机器的 Wi-Fi / GPU 固件零散且庞大。这个约束**反而因本决策变松了**：
   腾出来的 3–5 GB 余量正好可以把固件子集做大（代价见 §1 纪律 3），换来更多机器开箱可用。
6. **GPU 与本地推理已一并排除** —— CUDA 运行时 2–3 GB；既然不内置本地模型，GPU 栈
   也没有存在理由。若日后恢复本地推理，这项需要重新评估。
7. **密钥安全** —— 便携介质容易丢。加密 + 无痕模式 + 凭据永不入镜像是三条底线。
8. **平台例外** —— 部分笔记本（存储 / 无线）与 Apple Silicon 需要专有或未合并的驱动，
   Linux 便携系统上无法保证覆盖。支持矩阵要如实标注。
9. **"自适应"不等于"万能"** —— 能自动做的：驱动加载、网络模式、内存与并发预算、服务启停。
   不能自动做的：缺失的固件、冷门硬件。

## 7. 与你现有 HachileiOS 的关系 ⚠

两条线**建议并行但不合并**：

- **HachileiOS（xv6）** 继续作为 kernel / 机制学习与验证平台——它的价值在于你亲手实现调度、
  内存、信号这些机制，以及那套"每个批次可独立验证 + CI 门禁"的工程纪律。
- **便携式 Agent OS** 基于 Linux 不可变镜像实现——它的难点是工程集成与生态适配，不是内核机制。

**可以迁移的资产是方法论，不是代码**：批次化小步交付、每个改动都要有可验证的验收标准、
镜像/产物的可复现构建与签名、把踩到的每个编译器/工具链坑固化成检查项。
**不建议复用**的是内核代码——把 xv6 扩成能跑 Agent 的通用系统，成本会高出一个数量级。

## 8. 决策记录（ADR）

> 编号写作 `ADR-n`，与基线清单里的条目编号（A1–F7）**是两套命名空间**，不要混用。

### 已定

| # | 决策 | 决定 | 日期 | 主要影响 |
| --- | --- | --- | --- | --- |
| ADR-1 | 是否内置本地模型 | **不内置，纯云端** | 2026-10-01 | 镜像 5–7 → 2.5–5.3 GB；内存 4.5–5.0 → 1.0–1.5 GB；网络与密钥变成单点（§6 风险 1–3） |
| ADR-5 | 是否做 UI | **不做任何 UI**：无图形桌面、无 TUI、无 Web | 2026-10-01 | 唯一界面是命令行与 `--json`；省下的不只是首次开发的量，而是**每个能力都要维护两条路径**的持续投入 |
| ADR-6 | Agent 运行时 | **用现成框架，不自研** | 2026-10-01 | 自研范围收缩为「本机网关 + 工具/策略适配层」；框架**永远拿不到 provider 的 URL 与密钥** |

### 待定（三项都不阻塞开工，先按默认取值推进）

| # | 决策 | 默认取值 | 改选要动什么 | 最晚何时定 |
| --- | --- | --- | --- | --- |
| ADR-2 | v1 交付形态 | **虚拟机镜像** | 只改构建目标，不动架构——三种形态共用同一份 rootfs，另两种是 F3 的增量产物 | P1 开工时（改一次大约是一行配置） |
| ADR-3 | 目标宿主平台 | **VirtualBox** | 镜像格式（VMDK ↔ VHDX）与宿主侧网络配法（`VBoxManage` ↔ PowerShell ↔ `vmrun`）；宿主机需装的工具链 | P4 之前（此前只要有一个宿主能跑起来） |
| ADR-4 | API 密钥分发 | **用户自带（BYOK）** | 若改托管：新增中转服务、认证与计费，并重新评估数据出境面（§6 风险 2） | **P5 动手之前**（见下） |

**为什么这三项都不阻塞**
- ADR-2 只决定"产出什么格式"，不决定"系统里有什么"；
- ADR-3 是配置级改动，换宿主要动的是一行构建目标和一段宿主脚本；
- ADR-4 的 MVP 形态只有一种可能：用户自己填 key、加密存本地。托管是**在这一层之上加服务**，不是替换它。

**唯一需要提前想清楚的是 ADR-4。** 若最终选托管，"谁持有密钥"这条安全前提就变了，
E2（密钥加密存储）与 E3（镜像内不含凭据）的验收标准要跟着改写。
所以它必须在 **P5（持久化与密钥）动手之前**落定，否则那部分的测试用例要返工。
ADR-2/ADR-3 则可以一直推到对应阶段再定。

### ADR-5 / ADR-6 的两点说明（2026-10-01 记录；**只是记下来，暂不开工**）

**一、不做 UI，省下的是持续的投入，不只是首次开发的量。**
一个界面一旦存在，每个能力都要在两条路径上各实现一次、各测一次，
而且"文档与实现漂移"从此有了第二个战场。命令行 + `--json` 已经同时满足人看与脚本用；
`doctor`、验收脚本这类工具也都建立在它之上。

**二、用现成框架之后，自研的那一半反而更清晰了。** 分界线是：

| 归框架 | 归我们 |
| --- | --- |
| 工具循环、并行调用、重试预算 | 哪些文件可以离开本机（E8） |
| 上下文窗口管理与摘要 | 密钥存在哪、谁能读（E2） |
| 提示词编排、角色 | 工具沙箱与人工确认（清单 D4/D5/D7） |
| 各家 provider 的协议差异 | 用量与费用的记账（C7） |

**由此产生一条硬约束，写在这里以免以后踩**：框架**不能**拿到 provider 的 URL 与密钥。
一旦给了，密钥库、出网策略、provider 冷却、用量账本会被系统里自由度最大的那个组件绕过去，
审计日志也就不再是"什么离开了这台机器"的记录。正确接法是让框架指向**本机网关端点**

### 一条容易误解的边界：NAT / 桥接是宿主侧的决定

原始需求写的是"网络协议可以是 nat 或者 mirror，换环境自动更新"。
需要澄清一点：**在虚拟机形态下这两种模式由宿主设置，客机内部无法自己切换**——
客机看到的那张虚拟网卡永远只是"插着网线的以太网口"。

所以这条需求的正确落地方式是：
- 镜像**不做任何假设**，两种模式都按 DHCP 自适应（清单 B3 / B4 的验收标准据此写）；
- "自动切换"只发生在宿主侧，由部署脚本或文档指引承担；
- 若确实要求镜像自己切，需要另开一条宿主↔客机的通道（guest agent 或 virtio-serial 指令），
  属 V2 范畴，不进基线。
