# 便携式 Agent 操作系统：基线功能清单（43 项）

> 配套文档：`portable-agent-os.md`（技术路线与选型）。
> 本文回答的是"**要达到这种程度，最少需要哪些功能**"。
>
> **"基线"的定义**：不做这一项，产品就不能称为"便携式 Agent 操作系统"——要么根本跑不起来，
> 要么会在真实使用中立刻失败。**每项都配了可验证的验收标准**，没有验收标准的条目不算完成。

难度标记：低 / 中 / 高（"高"的一般是这类项目真正的时间黑洞）。

**已定决策（2026-10-01）：不内置本地模型，纯云端。** 本清单据此动了四处：
A5 不再是"禁用本地模型"而是"限制并发与上下文"；B6 从"离线仍可对话"改为
**"离线明确降级"**；新增 C8（流式中断恢复）与 E8（出网数据边界）——
因为本地模型这条退路取消后，**网络与密钥从"能力"变成了单点**。

## A. 引导与硬件适配（6 项）

| # | 功能 | 验收标准 | 难度 | 依赖 |
| --- | --- | --- | --- | --- |
| A1 | UEFI 与 Legacy 双模式引导 | 同一镜像在一台 UEFI 机器与一台 Legacy/CSM 机器上都能进到登录提示符 | 中 | — |
| A2 | Secure Boot 可引导 | 在一台开启安全启动的机器上，经 shim + MOK 注册后**无需关闭安全启动**即可引导 | 高 | A1 |
| A3 | 硬件画像 | 开机 30 秒内生成 `profile.json`：CPU 型号/核数、内存容量、磁盘与分区、网卡（含 MAC 与驱动名）、GPU | 低 | — |
| A4 | 按画像加载固件与模块 | 换到一台需要额外 Wi-Fi 固件的机器后，无线网卡自动可用，模块加载清单随画像变化 | 中 | A3 |
| A5 | 资源预算自适应 | 按宿主实际内存设定并发数与上下文窗口上限；**宿主只给 1 GB 时仍能启动**并明确提示能力受限；6 GB 护栏生效 | 低 | A3 |
| A6 | 换机变化检测 | 与该机器上次的画像做 diff，命令行提示"新增：网卡 X / GPU Y / 内存由 8 GB 变为 16 GB" | 中 | A3、E7 |

## B. 网络（6 项）

| # | 功能 | 验收标准 | 难度 | 依赖 |
| --- | --- | --- | --- | --- |
| B1 | 有线 DHCP | 插网线即获得地址，能解析域名并访问外网 | 低 | A4 |
| B2 | Wi-Fi WPA2 / WPA3 | 命令行可扫描、连接；密码错误给出明确可诊断的提示 | 中 | A4 |
| B3 | 虚拟机 NAT 模式 | 默认 NAT 下可访问外网，宿主无需额外配置；**客机侧不对模式做任何假设** | 低 | — |
| B4 | 虚拟机桥接（镜像）模式 | 切到桥接后，局域网内其他机器能直连其服务（例如用 curl 访问它的服务）；**与 NAT 模式共用同一镜像，无需重配客机** | 中 | B3 |
| B5 | DNS 与代理 | 可自定义 DNS 与 HTTP(S) / SOCKS 代理；配置错误时报错指向具体项 | 低 | — |
| B6 | 无网络降级 | 无网络时仍能启动，**命令行明确说明"仅文件与 shell 工具可用，无法对话"**，并把待发消息保留到网络恢复；不出现转圈或假可用 | 中 | B1、D1 |

> **一个边界**：NAT / 桥接的切换发生在**宿主侧**，客机无权也无法感知——
> 它看到的永远只是一张以太网卡。所以 B3 与 B4 的验收标准都写成
> "同一镜像在两种模式下都工作"，而不是"镜像能自己切换模式"；
> 宿主侧的切换由部署脚本或文档承担。若要求镜像自己切，
> 需另开一条宿主↔客机通道（guest agent 或 virtio-serial），属 V2，不进基线。

## C. 模型接入（8 项）

| # | 功能 | 验收标准 | 难度 | 依赖 |
| --- | --- | --- | --- | --- |
| C1 | OpenAI 兼容的本机端点 | `127.0.0.1:PORT/v1/chat/completions` 可用，任意 OpenAI SDK 改 base_url 即能直接调用 | 低 | — |
| C2 | ≥ 3 家云端 provider 可配置 | 3 家各填 key + base_url + 模型名后，都能成功完成一轮对话 | 低 | C1 |
| C3 | 模型列表查询与切换 | 能列出可用模型并在会话中途切换，切换后行为随之改变 | 低 | C2 |
| C4 | 流式输出 | 首字节延迟可观测，终端上逐字出现而非最后一次性刷出 | 中 | C1 |
| C5 | 超时 / 重试 / 限流 | 人为断网或返回 429 时按策略重试；超过上限返回明确错误，**不挂死** | 中 | C2 |
| C6 | 主备路由与回退 | 主 provider 不可用时**自动**切备用，日志记录切换原因（无本地回退，故为基线而非优化） | 中 | C2 |
| C7 | 用量与费用统计 | 每次调用记录 token 数与估算费用，可按会话与模型汇总（无本地模型时这是唯一的成本可见性） | 低 | C2 |
| C8 | 流式中断与恢复 | 对话中途断网：已收到的部分保留在会话文件里，重连后可重发，**不出现空白或永久转圈** | 中 | C4 |

## D. Agent 运行时（8 项）

| # | 功能 | 验收标准 | 难度 | 依赖 |
| --- | --- | --- | --- | --- |
| D1 | 多轮会话与上下文管理 | 超过上下文窗口时按既定策略截断或摘要，**不崩溃、不静默丢内容** | 中 | C1 |
| D2 | 系统提示与角色配置 | 可配置系统提示；两个不同角色对同一输入的产出可区分 | 低 | — |
| D3 | 工具注册与参数校验 | 新工具可声明式注册；参数不合法时返回**结构化错误给模型**，而不是抛异常 | 中 | — |
| D4 | 文件读写与目录列举工具 | 读写与列举被限定在工作目录内，越界访问被拒绝并留日志 | 低 | E5 |
| D5 | shell 执行工具 | 能执行命令并回传 stdout/stderr/退出码；默认需确认 | 中 | E5 |
| D6 | HTTP 请求工具 | 能发起请求；可配置出网白名单 | 低 | B5 |
| D7 | 危险操作需人工确认 | 未确认的写 / 删 / 执行一律不执行；用户拒绝后如实反馈给模型 | 中 | D4、D5 |
| D8 | 会话持久化与检索 | 重启后可继续既有会话；可按关键词检索历史 | 中 | E7 |

> **2026-10-01 决策：不自研 Agent 运行时，用现成框架（ADR-6）。**
> 上表 D1–D3（上下文管理、系统提示、工具注册与参数校验）改由框架承担；
> 我们的工作是**把 `minios tools` 已有的工具描述翻译成该框架的函数调用格式**。
> D4–D7（沙箱、确认、出网）继续留在自己手里——它们正是框架不该管、也管不好的部分。
> D8（会话持久化）同样归我们：会话要能在换机器后继续，就不能只存在框架的私有格式里。
> 另有 ADR-5：**不做 UI**，上述所有"告诉用户"的地方一律落到命令行输出。

## 关键路径（按依赖排出的最短可行顺序）

```
A3 硬件画像 ─┬─▶ A4 固件/模块 ──▶ B1/B2 网络
             ├─▶ A5 内存预算
             └─▶ A6 换机检测（需 E7）
E5 工具沙箱 ─┬─▶ D4 文件工具 ──▶ D7 确认机制
             └─▶ D5 shell 工具
C1 网关端点 ─┬─▶ C2 多 provider ─▶ C3/C5/C6/C7/C8
             ├─▶ C4 流式 ──▶ C8 中断恢复
             └─▶ D1 会话（B6 降级态也依赖它）
B1/B2/B3 网络 ──【硬依赖】──▶ C1：无网络就没有对话，批次 2 不再是"可选能力"
E1/E7 密钥与持久化 ──▶ D8 会话持久化、F6 备份
F1 只读+overlay ──▶ E4 无痕、F4 原子更新
F2 可复现构建 ──▶ F3 三形态
```

**建议的批顺序**（每条都能独立验证，与你 HachileiOS 的批次习惯一致）：
1. **能开机**：A1 → A3 → A5 → F1
2. **能联网**：A4 → B1 → B3 → B5　←　**纯云端下这一步是硬前置**，没做完谈不上第 3 批
3. **能对话**：C1 → C2 → C3 → C4 → **C6（主备）** → C8（中断恢复）
4. **能干活**：E5 → D3 → D4 → D6 → D7
5. **能留下东西**：E1 → E2 → E7 → D8
6. **能搬走**：F2 → F3 → F4
7. **能信**：A6 → E4 → E6 → F6 → F7
8. **能插任意机器**：A2 → B2 → B4（"高"难度的三项集中在这里）

## 容易被当成"基本"、但**不属于**基线的项

明确排除，避免范围失控：

| 项目 | 为什么不是基线 |
| --- | --- |
| 自研内核 / 自研文件系统 | 难点在固件与驱动生态，不在内核机制；自研会把周期从月变成年 |
| GPU 推理加速（CUDA / ROCm） | 唯一用途是本地推理，已随本地模型一并排除；日后若恢复再评估 |
| **本地模型（含 4B 级）** | **已决定不做**（2026-10-01）；直接省下 2.5 GB 镜像与约 3 GB 内存。代价见技术路线 §6 风险 1–3 |
| 自研 Agent 运行时（工具循环、上下文管理、重试预算） | **已决定用现成框架**（2026-10-01，ADR-6）。这部分最容易写错、也最不值钱；自研的只剩策略半层：网关、工具沙箱、密钥、出网、记账 |
| 多 Agent 编排 / 工作流编排 | 单 Agent 闭环跑通前谈编排是本末倒置 |
| 多机状态同步 | 涉及端到端加密与冲突合并，是独立课题 |
| **任何 UI（图形桌面 / TUI / Web）** | **已决定不做**（2026-10-01，ADR-5）。界面一旦存在，每个能力都要在两条路径上各实现一次；命令行 + `--json` 同时满足人看与脚本用 |
| 应用商店 / 插件市场 | 分发与签名体系是另一条产品线 |
| 移动端 / ARM 客户端 | 平台适配成本另计 |

## 每一项与 8 GB / 6 GB 预算的交互（决定取舍的地方）

| 若要做 | 对预算的影响 | 建议 |
| --- | --- | --- |
| ~~内置本地 4B 模型~~ | 镜像 +2.5 GB；内存 +3 GB 左右 | **已排除**（2026-10-01 决策） |
| 内置全量 `linux-firmware` | 镜像 +1.5 GB | 纯云端腾出的余量足够，**建议优先花在这里**（换来更多机器开箱可用） |
| 加入 GPU 支持 | 镜像 +2–3 GB | 已随本地模型一并排除；日后若恢复本地推理再评估 |
| 加入图形桌面 | 镜像 +1 GB 起 | **已排除**：不做任何 UI（ADR-5） |
| 三形态产物共用 rootfs | 不影响镜像体积（只影响构建产物） | 应当做，收益大成本低 |

**结论**：不内置本地模型后，8 GB 与 6 GB 这两个数字**大幅富余**——镜像约 2.5–5.3 GB、
常驻内存约 1.0–1.5 GB。纪律也随之改变：

- ~~本地模型只带 4B 级~~ **作废**：已不内置本地模型。
- **不装 PyTorch / CUDA** 依然有效，而且理由更强：Agent 与网关都不需要 GPU 栈，装了纯属浪费。
- **新纪律一：网络是硬依赖。** 断网 = 不能对话，密钥失效 = 不能对话。多 provider 主备、
  断线提示、流式中断恢复这三项因此从"优化"升级为基线（C6 / C8 / B6）。
- **新纪律二：余量的去向要记账。** 腾出来的 3–5 GB 不默认花掉，每一笔写回技术路线文档。
